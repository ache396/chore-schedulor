KEY CONCEPTS LEARNED
================================================================================

1. FASTAPI vs UVICORN
   - FastAPI = Web framework (defines routes, request handling, validation)
   - Uvicorn = ASGI server (runs the FastAPI app, handles HTTP)
   - You NEED both! FastAPI doesn't include a server
   - Analogy: Django (framework) needs Gunicorn (server)
   
   Running options:
   - Development: uvicorn app.main:app --reload
   - Production: gunicorn with uvicorn workers

2. DOCKER & VIRTUAL ENVIRONMENTS
   - DON'T need to "activate" .venv in Docker
   - Three ways to use venv in containers:
     a) uv run uvicorn ... (RECOMMENDED)
     b) ENV PATH="/app/.venv/bin:$PATH"
     c) Direct path: .venv/bin/uvicorn ...
   
   - Activation is for interactive shells only
   - Docker CMD exec form doesn't use shell

3. PYTHON SLIM IMAGES
   - python:3.14-slim doesn't include curl
   - Options:
     a) Use official uv image: ghcr.io/astral-sh/uv:python3.14-bookworm-slim
     b) Install curl temporarily, then remove it
     c) Copy installed binaries to /usr/local/bin/

4. SOURCE COMMAND IN DOCKER
   - 'source' is bash-specific (built-in)
   - Slim images use sh/dash, not bash
   - Exit code 127 = "command not found"

SYSTEM DESIGN & ARCHITECTURE
================================================================================

THE DATA FLOW (Request to Database)
-----------------------------------

Frontend → FastAPI → SQLAlchemy → PostgreSQL
   |          |          |            |
 (JSON)   (validates)  (ORM)      (stores)

Step-by-step breakdown:

1. FRONTEND SENDS REQUEST
   POST /jobs
   {
     "person": "Alice",
     "task": "Clean kitchen",
     "time": "2025-12-05T18:00:00",
     "message": "Don't forget the fridge"
   }

2. FASTAPI RECEIVES & VALIDATES
   - Endpoint receives HTTP request
   - Pydantic schema validates the JSON
   - Ensures required fields exist and types are correct
   - Returns 422 error if validation fails
   - Passes validated data to endpoint function

3. SQLALCHEMY TRANSFORMS TO DATABASE MODEL
   - Endpoint creates SQLAlchemy model instance
   - Example: new_job = Job(person="Alice", task="Clean kitchen", ...)
   - SQLAlchemy translates Python objects → SQL statements
   - Manages database session and transactions

4. POSTGRESQL STORES THE DATA
   - SQLAlchemy executes: INSERT INTO jobs ...
   - Database generates auto-increment fields (like job_id)
   - Data is persisted to disk
   - Returns success/failure

5. RESPONSE FLOWS BACK
   - PostgreSQL → SQLAlchemy (database row)
   - SQLAlchemy → Pydantic (Python object)
   - Pydantic → FastAPI (validated JSON)
   - FastAPI → Frontend (HTTP response)
   - Usually returns the created job with its new job_id

THE THREE LAYERS OF DATA REPRESENTATION
---------------------------------------

You need THREE representations of the same data:

1. PYDANTIC SCHEMA (schemas.py) - API Layer
   Purpose: Validation and serialization
   - Validates incoming requests
   - Serializes outgoing responses
   - Auto-generates API documentation
   - Type hints for IDE support
   
   Two schemas per resource:
   
   a) CREATE SCHEMA (Input from frontend)
      class JobCreate(BaseModel):
          person: str
          task: str
          time: datetime
          message: str | None = None
      
      - NO id field (database generates it)
      - Only fields user can set
      - Used in POST requests
   
   b) RESPONSE SCHEMA (Output to frontend)
      class Job(BaseModel):
          id: int
          person: str
          task: str
          time: datetime
          message: str | None = None
          created_at: datetime
          
          class Config:
              from_attributes = True  # Converts from SQLAlchemy
      
      - Includes id and auto-generated fields
      - Represents full database record
      - Used in GET/POST responses

2. SQLALCHEMY MODEL (models.py) - Database Layer
   Purpose: Object-Relational Mapping (ORM)
   - Defines database table structure
   - Maps Python classes to SQL tables
   - Handles relationships between tables
   - Manages database operations (CRUD)
   
   Example structure:
   class Job(Base):
       __tablename__ = "jobs"
       
       id = Column(Integer, primary_key=True, index=True)
       person = Column(String)
       task = Column(String)
       time = Column(DateTime)
       message = Column(String, nullable=True)
       created_at = Column(DateTime, default=datetime.utcnow)

3. POSTGRESQL TABLE - Storage Layer
   Purpose: Physical data storage
   - Actual table in database
   - Columns, constraints, indexes
   - ACID compliance (transactions)
   - Data persistence

FASTAPI ENDPOINT STRUCTURE
--------------------------

Basic pattern:

@app.post("/jobs", response_model=Job, status_code=201)
async def create_job(job: JobCreate, db: Session = Depends(get_db)):
    # job parameter is validated automatically by Pydantic
    # db parameter is database session injected by FastAPI
    
    # 1. Convert Pydantic schema to SQLAlchemy model
    db_job = JobModel(**job.dict())
    
    # 2. Add to database session
    db.add(db_job)
    
    # 3. Commit transaction
    db.commit()
    
    # 4. Refresh to get generated fields
    db.refresh(db_job)
    
    # 5. Return (automatically converted to response_model)
    return db_job

Key concepts:
- request validation via type hints (job: JobCreate)
- dependency injection (db: Session = Depends(get_db))
- response_model for output validation
- status_code for HTTP response codes
- automatic JSON serialization

DATABASE SESSION MANAGEMENT
---------------------------

Use dependency injection for database sessions:

# In database.py
from sqlalchemy.orm import sessionmaker

SessionLocal = sessionmaker(bind=engine)

def get_db():
    db = SessionLocal()
    try:
        yield db
    finally:
        db.close()

# In endpoints
def create_job(job: JobCreate, db: Session = Depends(get_db)):
    # db is automatically created and cleaned up

This ensures:
- Sessions are properly closed
- No connection leaks
- Thread-safe operations
- Transaction management

TESTING STRATEGY
----------------

Current phase: Testing API layer with minimal database interaction

Approach 1: IN-MEMORY STORAGE (Simplest for initial testing)
   - Store jobs in Python list/dict
   - Test API contract without database complexity
   - Fast iteration and debugging
   - Good for validating schemas and endpoints

Approach 2: TEST DATABASE
   - Use SQLite in-memory or separate test PostgreSQL
   - Test full integration
   - Verify database operations
   - More realistic but more setup

Approach 3: MOCKING
   - Mock database layer
   - Test API logic in isolation
   - Fast but requires mock setup

Testing tools:
- pytest: Test framework
- TestClient (from FastAPI): Test HTTP endpoints
- pytest-asyncio: Test async endpoints

Example test structure:
from fastapi.testclient import TestClient
from app.main import app

client = TestClient(app)

def test_create_job():
    response = client.post("/jobs", json={
        "person": "Alice",
        "task": "Clean kitchen",
        "time": "2025-12-05T18:00:00"
    })
    assert response.status_code == 201
    assert response.json()["person"] == "Alice"

IMPORTANT DESIGN DECISIONS TO CONSIDER
--------------------------------------

1. ID GENERATION
   Q: Should frontend send job_id, or database generate it?
   A: Database should generate (auto-increment or UUID)
   Why: Prevents conflicts, ensures uniqueness

2. VALIDATION
   Q: What if invalid person name?
   Q: Should time be in the future?
   Q: Required vs optional fields?
   Think about: Business logic validation in addition to type checking

3. TIMESTAMPS
   Q: created_at - who sets it?
   A: Database default (datetime.utcnow)
   Q: updated_at - do you need it?
   Q: completed_at - when job is done?

4. STATUS MANAGEMENT
   Q: How to track job lifecycle?
   Options: 
   - Boolean: is_completed
   - Enum: pending, in_progress, completed, cancelled
   - State machine: Define valid transitions

5. ERROR HANDLING
   Q: What happens when database is down?
   Q: What if duplicate job submitted?
   Q: How to communicate errors to frontend?
   Use: HTTPException with appropriate status codes

6. DATA RELATIONSHIPS
   Q: Should "person" be just a string or reference to Users table?
   Q: Task categories - separate table?
   Q: Recurring jobs - how to model?
   Think about: Normalization vs simplicity
